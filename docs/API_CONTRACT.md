# FitBook API - contract for the mobile app

Generated by `npm run contract` from the live route definitions (OpenAPI) and real responses captured on the seeded
database. Interactive docs: `http://localhost:3000/docs`, machine-readable spec: `docs/openapi.json`.

## 1. Base URLs (local development)

| Where the app runs       | REST base URL                     | Socket.IO URL              |
| ------------------------ | --------------------------------- | -------------------------- |
| iOS Simulator            | `http://localhost:3000/api/v1`    | `http://localhost:3000`    |
| Android Emulator         | `http://10.0.2.2:3000/api/v1`     | `http://10.0.2.2:3000`     |
| Real device (same Wi-Fi) | `http://<mac-lan-ip>:3000/api/v1` | `http://<mac-lan-ip>:3000` |

Find the Mac's LAN IP with `ipconfig getifaddr en0`. Debug builds of React Native allow plain HTTP to these hosts.

## 2. Conventions

- JSON only. Ids are 24-char hex strings (`id`).
- Dates are ISO 8601 UTC strings (`2026-11-03T15:00:00.000Z`). Show them in the device time zone. Weekly
  availability times (`"09:00"`) are local to the coach's `homeArea.timezone`.
- Money: `{ "amountCents": 8500, "currency": "USD" }` -> display `$85.00`.
- Paged lists: `{ items, page, pageSize, total }` with query `page`, `pageSize` (max 50).
- Chat messages use a cursor: `{ items, nextCursor }`, newest first; pass `before=<nextCursor>` for older ones.
- Bookable start times are on a 30-minute grid and at least 2 hours in the future.

## 3. Authentication

Email + password sign-in takes two steps: the password, then a 6-digit code sent by email. Tokens are issued only
after the code is verified (on sign up the code also confirms the email).

1. `POST /auth/register` (role `client` or `coach`, plus `homeArea`: city, 2-letter state, IANA time zone)
   -> `201 { verification }`, or `POST /auth/login` -> `200 { verification }`. No tokens yet.
   `verification = { id, purpose: "signup" | "login", email, codeLength: 6, expiresAt, resendAvailableAt }`.
   Login of an account whose email is not confirmed yet returns `purpose: "signup"`.
   Registering again with an unconfirmed email is allowed (fix a typo and resubmit): the account is overwritten.
2. Code screen: when 6 digits are entered call `POST /auth/verify { verificationId, code }` -> `{ user, tokens }`
   (same shape as the old login response). Errors: `VERIFICATION_CODE_INVALID` (`details.attemptsLeft`),
   `TOO_MANY_ATTEMPTS` (5 wrong codes, a resend gives a new code), `VERIFICATION_CODE_EXPIRED` / `NOT_FOUND`
   (go back to sign in / sign up). The code lives 10 minutes (`expiresAt`), the whole verification 30 minutes.
3. "Resend code" is enabled from `resendAvailableAt` (60 s after each send): `POST /auth/verify/resend
{ verificationId }` -> `{ verification }` (same id, new dates; the previous code stops working). Too early ->
   `429 RATE_LIMITED` with `details.retryAfterSeconds`; after 5 resends -> `VERIFICATION_CODE_EXPIRED`.
   If the email with the code cannot be sent, register / login / resend answer `503 EMAIL_DELIVERY_FAILED`
   (stay on the form, show an alert, let the user retry; nothing was sent, so there is no code screen).
   Local development: the email arrives in Mailpit (http://localhost:8025) and the code is printed in the server log;
   with `AUTH_DEV_FIXED_CODE=000000` in `.env` the code `000000` is accepted too (never in production).
4. Send `Authorization: Bearer <accessToken>` on every request (access token lives 15 minutes).
5. On `401 TOKEN_EXPIRED` call `POST /auth/refresh` with the refresh token **once**, store **both** new tokens
   (refresh tokens rotate; an old one is rejected and revokes the session), then retry. If refresh fails -> sign out.
   Refresh never asks for a code.
6. `POST /auth/logout` with the refresh token on sign out.
7. Google / Apple (no email code): send the provider token to `/auth/google` (`idToken`) or `/auth/apple`
   (`identityToken`, plus `firstName`/`lastName` from the first Apple sign-in) -> `{ user, tokens }`. If
   `user.onboardingCompleted` is false, show onboarding and call `POST /me/onboarding` with `role` and
   `homeArea`; until then other endpoints return `403 ONBOARDING_REQUIRED`.
8. Forgot password: `/auth/password/forgot` (always 204) -> 6-digit code by email -> `/auth/password/verify-code`
   -> `resetToken` -> `/auth/password/reset` -> `{ user, tokens }`: signed in, no extra code (all other sessions
   are signed out).
9. Change password: `PATCH /me/password` -> `{ tokens }`: store the new pair; this device stays signed in, other
   devices are signed out.

The role decides the app: **client** -> coach catalog, booking, my calendar, chat, settings; **coach** -> work
calendar (schedule), sessions with participants and notes, training types and prices, availability, cancellation
policy, chat, settings. Theme preference is stored in `user.settings.theme` (`light | dark | system`).

## 4. Booking flows (client)

- **Individual:** `GET /coaches/:id` (training types) -> `GET /coaches/:id/slots?sessionTypeId&from&to` ->
  `POST /bookings { sessionTypeId, startAt, isTrial?, location? }`.
- **Free trial:** check `GET /me/trial`; book with `isTrial: true` (individual only, one per email, ever).
  Trial bookings are `confirmed` immediately with price 0.
- **Group:** `GET /coaches/:id/group-sessions?from&to` (shows `spotsLeft`) -> `POST /bookings { sessionId }`.
- **Series:** `POST /bookings/series/preview` (weekdays 0 = Sunday, local time, weeks 1-12) shows free / taken
  dates -> user picks -> `POST /bookings/series { ..., dates }` -> `POST /bookings/series/:id/pay`.
- **Manage a series:** `GET /bookings/series/:id` (client or its coach) -> `Series { sessionType, coach, weekdays,
time, timezone, format, bookings, upcomingCount, nextAt, lastAt, canExtend, extendFrom }`.
  `POST /bookings/series/:id/cancel { reason? }` cancels every upcoming booking with the usual rules (refunds,
  credits back) -> `{ cancelled, kept }` (kept = past the deadline; none cancelled -> `CANCELLATION_WINDOW_PASSED`).
  New day / time for all upcoming: `POST /bookings/series/:id/reschedule/preview` and `/reschedule` with
  `{ weekdays, time, startDate }`: the movable bookings (reschedulable, by start) are paired in order with the first
  dates of the new pattern; free ones move (payment, credits, notes stay), taken ones stay -> `{ moved, kept }`; the
  pattern is updated. Extend: `POST /bookings/series/:id/extend/preview { weeks }` (from `extendFrom`, same items
  as the series preview) and `POST /bookings/series/:id/extend { weeks, dates, useCredits? }` -> same as
  `POST /bookings/series` with the same `seriesId`; pay new bookings with `/bookings/series/:id/pay`.
  `canExtend: false` -> `SERIES_NOT_EXTENDABLE`.
- **Mock payment:** paid bookings start as `pending_payment` with `expiresAt` (15 minutes); call
  `POST /bookings/:id/pay`. Unpaid bookings are released automatically (`cancelled`, `cancelledBy: system`).
- **Location:** individual bookings may pass a `location` chosen on the map (Google Places), including an optional
  `comment` (meeting point). Otherwise the training type or coach default location is used.
- **Cancellation:** use `booking.cancellable` and `booking.cancelDeadline` to show the button and the deadline.
  Confirmed bookings can be cancelled only before the coach's `freeCancelHours`; unpaid ones any time before start.
- **Reschedule:** while `booking.reschedulable` (same window as cancelling: before `cancelDeadline`, or before the
  start for unpaid bookings) the client can move the booking: `POST /bookings/:id/reschedule` with
  `{ startAt }` (individual: a free slot of the same type from `/coaches/:id/slots`; the booking's own slot does
  not block it) or `{ sessionId }` (group: another upcoming group session of the same type with free places;
  `session.sessionTypeId` tells which). Same `id`, payment, trial, price, notes, location and series; the old
  slot / place is released; `rescheduledAt` is set. Errors: `RESCHEDULE_WINDOW_PASSED`, `SLOT_UNAVAILABLE`,
  `SESSION_FULL`, `NOT_FOUND` (target group session), `VALIDATION_ERROR` (none / both fields, same time).
- **Refunds (mock, instant):** cancelling a **paid** booking always returns the full price:
  `payment.status` becomes `refunded` and `payment.refundedAt` is set. The client can cancel only before
  `cancelDeadline` (after it -> `409 CANCELLATION_WINDOW_PASSED`, nothing changes); cancellations by the coach
  (single booking or a whole group session) or by the system are refunded at any time. Unpaid
  (`unpaid`) and free (`not_required`, trial) bookings have nothing to refund and keep their status.
  Show e.g. "Refunded $65.00" using `price` when `payment.status === 'refunded'`.
- **Device calendar:** `GET /bookings/:id/calendar-event` returns title, start/end, location and notes for the
  native "add event" dialog.
- **Calendar tab:** `GET /bookings?scope=upcoming` (ascending) and `GET /bookings?scope=past` (descending).
- **Notes:** `GET/POST /bookings/:id/notes`, `PATCH/DELETE /notes/:id`; phases `before` and `after`; both
  the coach and the client can edit; `lastEditedBy` tells who changed it.

Booking statuses: `pending_payment` -> `confirmed` -> `completed`, or `cancelled` (by `client`, `coach`
or `system`), or `no_show` (the coach marked that the client did not come; see 5a).

## 3a. Catalog: filters, sorting, next available

- `GET /coaches` filters (all combine): `search`, `specialization`, `kind`, `state`, `city`, `favorites`,
  `format`, `priceMin` / `priceMax` (cents: an active type in the range), `timeOfDay=morning,afternoon,evening`
  (free individual slot or group place in the next 14 days starting in that part of the day in the viewer's time
  zone: morning 05:00-11:59, afternoon 12:00-16:59, evening 17:00-22:59), `trial=true` (has an active individual
  type), `language` (case-insensitive). `sort`: `recommended` (default: my state first, then rating),
  `rating`, `price_asc`, `price_desc` (by `priceFrom`), `next_available` (`null` last). `total` counts
  the filtered coaches; paging follows the sort.
- Coach objects (catalog, profile, favorites) have `nextAvailableAt` (earliest free individual slot in the next 14
  days; for group-only coaches the earliest free group place; `null` if none) and `languages`.
- `GET /coaches/filters` -> `{ languages, price { min, max } }` for the filter screen.
- Map: `GET /coaches?bbox=minLng,minLat,maxLng,maxLat` returns coaches whose default location is inside the box
  (online-only coaches are never returned with bbox), combined with all filters and sorting; `pageSize` up to 100
  with bbox (50 otherwise). Invalid bbox -> `VALIDATION_ERROR`. Coach objects have
  `location { lat, lng, name, city, state }` (public part of the default location, no meeting-point comment) or
  `null`.

## 3b. Online trainings

- Coach profile: `online { enabled, meetingUrl }` (`PUT /coach/profile`; enabling needs an https
  `meetingUrl` up to 500 characters -> `VALIDATION_ERROR` `details.fields.meetingUrl`). Turning online off while
  active `online` / `both` types exist -> `ONLINE_TYPES_ACTIVE`. A coach with online on needs no
  `defaultLocation` to publish (completeness requires a default location or online).
- Training type `format`: `in_person` (default) | `online` | `both` (the client chooses; individual only,
  group + both -> `VALIDATION_ERROR`). `online` / `both` need online on (`ONLINE_NOT_ENABLED`).
- Booking an individual training: `format: "in_person" | "online"` in `POST /bookings`,
  `/bookings/series/preview` and `/bookings/series` - required for `both` types, must match single-format types.
  Group bookings take the session's format. Online bookings have `session.location: null`; reschedule keeps the format.
- Booking: `format`, `session.format` and `meetingUrl` (the coach's current link, online only; only the client and
  the coach of the booking ever see it). Calendar event of an online booking: `location: null`, `meetingUrl` and the
  link in `notes`.
- Public coach objects (catalog, profile, favorites): `formats: ["in_person", "online"]` from active types. Filter:
  `GET /coaches?format=online` / `format=in_person`. The meeting link is never public.

## 4a. Packages (credits)

- A coach sells packages (`GET /coaches/:id` -> `packages`, active only): e.g. 10 credits for $700, valid
  `validityDays` after purchase. 1 credit = 1 training with this coach of any type (individual or a group place).
- `POST /packages/:id/purchase` (mock payment, instant) -> `ClientPackage`; inactive -> `PACKAGE_INACTIVE`.
  `GET /me/packages?coachId=` -> `{ items, creditsAvailable }` (usable purchases first, soonest to expire first).
- Book with a credit: `useCredits: true` in `POST /bookings` (individual or group) or `POST /bookings/series`
  (1 credit per booked date, `INSUFFICIENT_CREDITS` with `details.creditsAvailable` and nothing booked). The
  booking is `confirmed` immediately: `payment = { status: "paid", method: "credits", clientPackageId }`; the
  credit comes from the purchase that expires first. No usable credit -> `NO_CREDITS`. Not with `isTrial`.
- When a paid booking would be refunded (client before the deadline, coach, system), a credit booking gets its credit
  back into the same purchase instead (`payment.status = "refunded"`); if that purchase expired meanwhile the
  credit is lost. Rescheduling keeps the credit.
- Coach: `GET/POST /coach/packages`, `PATCH/DELETE /coach/packages/:id` (changes apply to new purchases; a bought
  package is deactivated instead of deleted).

## 4b. Waitlist (full group sessions)

- `GET /coaches/:id/group-sessions` items have `waitlist { count, myStatus, myPosition, offerExpiresAt }`.
  When `spotsLeft === 0` and `myStatus` is null, offer "Join waitlist": `POST /group-sessions/:id/waitlist` ->
  `WaitlistEntry` (`SESSION_NOT_FULL` if places are free - book instead, `ALREADY_BOOKED`,
  `ALREADY_ON_WAITLIST`). Leave any time: `DELETE /group-sessions/:id/waitlist` (204).
- When a place frees up (cancellation by anyone, or a reschedule to another session) the first `waiting` client
  gets `status: "offered"`: the place is held for them until `offerExpiresAt` = min(now + 2h, start - 15 min);
  everybody else keeps seeing `spotsLeft: 0` and gets `SESSION_FULL`. The offered client books with the usual
  `POST /bookings { sessionId }` (`useCredits` works too); the entry becomes `booked`. An expired or declined
  (left) offer passes to the next client. If less than 15 minutes remain, the place is simply free for everybody.
  When the session starts or is cancelled every entry becomes `expired`.
- `GET /me/waitlist` -> `{ items }` with `waiting` and `offered` entries (offers first). Socket.IO
  `waitlist:offered { entry }` is sent to the client who got an offer (show an in-app notification).

## 4d. Progress (client) and client progress (coach)

- `GET /me/progress?weeks=12` (4-52) -> `{ totals { completed, thisMonth, coaches }, goal { trainingsPerWeek },
thisWeek { weekStart, completed, planned }, streakWeeks, weekly [{ weekStart, completed }] }`. A training counts
  when its booking is `completed`; `planned` = `confirmed` bookings later this week. Weeks start on Monday in
  the client's `homeArea.timezone` (`weekStart` = that Monday, YYYY-MM-DD). `weekly` has exactly `weeks`
  items, oldest first, the last one is the current week. `streakWeeks` = consecutive weeks meeting the goal
  (`>= 1` training without a goal), ending with the last finished week, or the current week if its goal is met.
- `PUT /me/goal { trainingsPerWeek: 1..14 | null }` -> `{ trainingsPerWeek }`.
- Measurements (fixed units): `weight` lb 50-700, `body_fat` % 2-70, `waist` in 15-80, at most 1 decimal.
  `POST /me/measurements { type, value, measuredAt?, note? }` -> 201; the same type on the same local day replaces the
  value -> 200 (same `id`). `measuredAt` defaults to today in the client's time zone, never in the future.
  `GET /me/measurements?type&limit` (newest first, limit <= 200), `DELETE /me/measurements/:id`.
- Coach: `GET /coach/clients/:clientId/progress?weeks` - same body, but `totals` and `weekly` count only
  trainings with this coach (`thisWeek` and `streakWeeks` are the client's overall), plus
  `measurements.latest { weight, body_fat, waist }`; `GET /coach/clients/:clientId/measurements`. Only for clients
  who have (or had) a booking with the coach, otherwise `NOT_FOUND`.

### 5a. No-show

- From the start of a training until `noShowDeadline` (start + 48h) the coach can mark a client of a
  `confirmed` / `completed` booking as a no-show: `POST /coach/bookings/:id/no-show { refund }` -> Booking with
  `status: "no_show"` and `noShow { markedAt, refunded }`. `refund: true` returns the payment like a coach
  cancellation (`payment.status = "refunded"`; a credit goes back to its package if not expired); `refund: false`
  keeps it (a credit stays used). Ignored for trial / free bookings. Group sessions: per participant booking.
- `DELETE /coach/bookings/:id/no-show` removes it inside the same window, only if it was not refunded
  (`NO_SHOW_REFUNDED`); the booking goes back to `completed` (ended) or `confirmed`.
- Booking and schedule participants have `noShow`, `noShowMarkable`, `noShowUndoable` (true only for the
  booking's coach), `noShowDeadline`. Without a mark nothing changes: the training becomes `completed`.
- No-shows do not count in progress, do not allow a review and are not counted in `/coach/clients`.

## 8. Enums

- Role: `coach | client`; Theme: `light | dark | system`; Training kind: `individual | group`
- Training format: `in_person | online`; Training type format: `in_person | online | both`
- Booking status: `pending_payment | confirmed | cancelled | completed | no_show`; Payment status: `unpaid | paid | refunded | not_required`; Payment method: `mock | credits`
- Session status: `scheduled | cancelled | completed`; Note phase: `before | after`
- Specializations: `strength`, `yoga`, `running`, `boxing`, `pilates`, `crossfit`, `swimming`, `tennis`, `hiit`, `mobility`
- States: 2-letter US state codes (`IL`, `NY`, ...); country is always `US`.
